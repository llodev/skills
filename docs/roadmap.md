# @llodev/skills — Roadmap

Date: 2026-08-21. Baseline: `main` at core v1.16.0 / asana v1.11.0 / trello v1.11.0 / jira v1.3.0 / linear v1.2.0 / meta v3.1.1 (PRs #71–#95 merged). Forward-looking roadmap — single source of truth for **what's next**. Per-package `CHANGELOG.md` (auto-generated by Changesets) is the canonical history; this doc stays focused on the future.

Sections §1–§8 cover the `pm-tasks-*` family. The repo is multi-family — families beyond `pm-tasks-*` are tracked in **§9** (`django-*`, `ts-ddd-*`).

**Proposed P0:** transport conformance across asana / jira / linear (§3). The first live dogfood of Trello found a response-shape bug that 569 green unit tests had missed, because every transport is tested against mocks its own author wrote. Trello is fixed; the other three still carry the untested assumption. Not yet committed — see §3 for the case and the alternative.

## 3. Next P0 — transport conformance (proposed)

The previous P0 was "stabilize and dogfood the 5 released adapters." That ran, and it paid: the first live dogfood of a Trello batch publish surfaced **v1.10.1** — a transport that reported `failed` on writes that had already landed, leaving orphan cards, comments, and checklists on the board with an audit trail claiming `ok: false`. 569 unit tests were green throughout, because the stubs were hand-written to the shape the author assumed rather than the shape the server returns.

That makes the follow-on priority concrete rather than speculative. **Asana, Jira, and Linear ship the identical pattern and have never been live-verified.** The same class of defect is more likely present than not, and it is the worst kind: silent, data-affecting, and invisible to the test suite.

**Proposed scope (C1 + C2 + C3):**

Conformance has two independent halves, and the coverage today is uneven on both:

| Adapter    | Request params guarded (mock rejects unknown keys) | Response shape captured from a live run |
| ---------- | -------------------------------------------------- | --------------------------------------- |
| **jira**   | ✅ `CREATE_JIRA_ISSUE_ALLOWED_KEYS`                | ❌                                      |
| **linear** | ✅ `SAVE_ISSUE_ALLOWED_KEYS`                       | ❌                                      |
| **trello** | ❌                                                 | ✅ (v1.10.1)                            |
| **asana**  | ❌                                                 | ❌                                      |

Request guards matter because the real tool schemas set `additionalProperties: false` — a wrong key is fatal, not ignored. Response fixtures matter because that is exactly what bit Trello. No adapter has both.

1. **Capture** verbatim response shapes from each live MCP (asana, jira, linear) for every write verb the adapter maps.
2. **Replace** hand-authored stubs with the captured fixtures, and add the allowed-key request guard to asana and trello so all four adapters cover both halves.
3. **Unwrap** any envelope the live server actually returns, accepting a bare resource too, so a caller that unwraps on its own keeps working (the Trello v1.10.1 shape).
4. **Enforce `autonomous.allow` in the core runtime** (C2) so the documented safety contract holds on the headless path, not just in agent narration.
5. **Document a live smoke** per adapter (C3) as the promotion gate for any future transport change.

Sequencing: one release per adapter, `pmt-<skill>-v<X.Y.Z>` per the repo's branch convention. Asana first — its config↔MCP workspace mismatch (`.asana.json` targets a workspace the connected MCP does not authenticate to) is itself a blocker that has to be resolved before any live verification of that adapter is possible.

**The alternative**, if field demand outweighs the risk: pick a 6th adapter from §4 (`github-projects` is the cheapest high-value one). That is a defensible call, but it widens a surface whose existing width is not yet verified. Recommend conformance first.

The remaining scaffolds — `pm-tasks-{clickup,notion,monday,bitrix24,todoist}` plus the `github-projects` note (§4) — stay a demand-driven pool. The next one built is whichever gets pulled by actual need, not a pre-picked slot.

## 9. Beyond pm-tasks — new skill families

The repo is no longer single-family. `pm-tasks-*` stays the primary track; new families ship as new skills under the flat `skills/` directory (one directory per skill, the convention skill indexers expect), with family membership carried by the name prefix and each skill's `metadata.family` field rather than by directory nesting. Each skill versions independently (own `CHANGELOG.md`, own changeset, branch = version) and is registered in `pnpm-workspace.yaml` + `.claude-plugin/marketplace.json`. The `marketplace-parity` gate resolves each package dir from its `source.path`, so it's layout-agnostic.

### `django-*` — Django design knowledge skills

Pure knowledge skills (no MCP / config / init) that inject expert Django decisions — trade-offs, anti-patterns, decision trees — rather than basic ORM syntax. Each skill owns exactly one design concern so they compose without overlapping coverage.

| Skill                  | Concern                                                                                                                                                           | Status              |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------- |
| `django-schema-design` | Database schema — PK strategy (incremental / UUIDv4 / UUIDv7 with insert-locality trade-offs), indexes (composite/covering/partial), constraints, safe migrations | ✅ shipped `v0.2.0` |
| `django-model-design`  | Model layer — relationships, managers/querysets, fat-vs-thin models, business-logic placement                                                                     | 🔜 planned          |

The `schema-design` / `model-design` split is deliberate: DB-level decisions vs. ORM/model-layer decisions, no dimension covered twice. `django-schema-design` is the only member shipped and has had no functional release since `v0.1.0` (`v0.2.0` was a metadata refresh) — the family is dormant until `django-model-design` is scoped with the maintainer.

### `ts-ddd-*` — TypeScript DDD design knowledge skills

Project-agnostic Domain-Driven Design guides for TypeScript codebases — one skill per architectural layer (entity, value object, DTO, use case, repository, controller, domain service) plus a read-side CQRS companion. Pure knowledge skills (no MCP / config / init): they activate on the prompt and inject expert decisions (`Result`-based validation, `cloneWith` state transitions, enum-backed closed sets, Firestore/InMemory adapter pairs) rather than basic TypeScript syntax.

All 9 packages shipped together at `v0.1.0` (PR #64) and have not moved since: `ts-ddd-entity`, `ts-ddd-value-object`, `ts-ddd-dto`, `ts-ddd-use-case`, `ts-ddd-repository`, `ts-ddd-controller`, `ts-ddd-domain-service`, `ts-query-cqrs`, plus the `@llodev/ts-ddd` meta-package that installs them all.

The family has no committed next step. It was generalized out of a private monorepo to the `@acme/` placeholder convention, so the open question is whether real-world use outside that origin justifies a `v0.2.0` — same demand-driven test applied to the adapter pool in §4.
