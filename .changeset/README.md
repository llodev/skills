# Changesets

Folder generated by `@changesets/cli`. Used to record version-bump intent across the workspace.

## Quick guide

Three commands, run in order:

```bash
make changeset          # 1. record intent (interactive)
make release-version    # 2. apply bumps + write CHANGELOGs
make release-publish    # 3. publish to npm
```

### 1. `make changeset` — record intent

Interactive prompt:

- Which packages changed?
- For each: `major` / `minor` / `patch`?
- Summary (one or two lines).

Writes a file like `.changeset/<random-name>.md`. **Commit it together with the code change.** Nothing in `package.json` or `CHANGELOG.md` is touched yet — this step only records the intent.

Multiple changesets can pile up between releases; they're consolidated at version time.

### 2. `make release-version` — apply the bumps

Reads every pending `.changeset/*.md`:

- bumps the version field in each affected `package.json`,
- prepends an entry to each affected `CHANGELOG.md`,
- deletes the consumed `.md` files,
- runs `pnpm version:sync` to keep workspace dependency ranges aligned.

Output is one big commit's worth of edits. Review the diff before committing as `chore(release): vX.Y.Z`.

### 3. `make release-publish` — push to npm

Publishes every workspace package whose `version` is ahead of what's on npm. Requires npm auth (handled by CI in `release.yml` — locally you need `npm login`).

## Quality gate — skill-judge

`make release-version` is prerequisite-chained to `make pre-release`, which enforces the [skill-judge](../scripts/skill-judge-check.mjs) ratchet: if any `pm-tasks/*/SKILL.md` was modified on this branch vs `origin/main` AND `scripts/skill-judge-baseline.json` was NOT updated in the same range, the gate blocks the release.

The flow when SKILL.md changed:

1. Run `make skill-judge` with current scores piped in as JSON (`{<path>: <score 0–100>}`) — agent scores each modified SKILL.md via the `skill-judge` skill, pipes the JSON to the make target.
2. Compare against `scripts/skill-judge-baseline.json`. Verdicts: **PASS** (Δ ≥ 0), **WARN** (drop within tolerance), **FAIL** (regression beyond tolerance), **NEW** (no baseline entry).
3. **If Δ ≥ +3 for any modified skill**: ratchet that entry in `scripts/skill-judge-baseline.json` (bump `version` + `capturedAt`) and commit on this branch — that's what unblocks the gate.
4. **If drift is noise (Δ ∈ [-2, +2])**: bypass with `SKIP_SKILL_JUDGE_GATE=1 make release-version` and document the justification in the next changeset summary.

The gate prints exactly which files triggered it and which action is required, so there's no guessing.

## Cheatsheet

| Want to …                                       | Run                                                    |
| ----------------------------------------------- | ------------------------------------------------------ |
| Record a fix that touches `pm-tasks-asana` only | `make changeset` → select asana → patch                |
| Record a coordinated fix across all 3 packages  | `make changeset` → multiselect all → patch             |
| Release a major (breaking) bump                 | `make changeset` → choose `major` for the affected pkg |
| Empty changeset (rare; just to test)            | `pnpm changeset --empty`                               |
| Inspect what the next release will look like    | `pnpm changeset status`                                |

## Common gotchas

- **Forgot to make a changeset?** No problem during the same PR — add it later with `make changeset`, commit the `.md`.
- **Manually edited `package.json` version?** Safe ONLY if `.changeset/` has no pending `*.md`. Otherwise `release-version` will double-bump on top of your edit.
- **Workspace deps (`"workspace:^"`) on inter-package imports** are rewritten to real ranges at publish time — don't pre-resolve them by hand.
- **`commit: false` in `config.json`** is intentional. Changesets don't auto-commit; you control which commit ships the bump.
